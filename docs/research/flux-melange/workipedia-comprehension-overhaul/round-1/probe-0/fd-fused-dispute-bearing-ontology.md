# fd-fused-dispute-bearing-ontology — round 1

## Findings Index

- [P1] alias-apparatus-precedent-unused-for-edges — a working, live redirect/citation-continuity mechanism already exists for issue identity and is never extended to connections, though it is the cheapest available fix for Ruling 2's erasure problem (§Key Decisions #2)
- [P0] reciprocal-pair-shape-conflates-loop-with-contradiction — the connections[] schema represents a verified reinforcing two-cycle and an unreconciled contradictory pair with the exact same two-line shape, so Jev's own 30-vs-129 split (Ruling 8) cannot be recovered from the data once written (§Key Decisions #2, #8)

## Findings

### alias-apparatus-precedent-unused-for-edges

- **Severity**: P1
- **Where**: `scripts/data/validate-issue-data.ts:28-31` (`RedirectIndex`: `aliasToCanonical`, `mergedToCanonical`, `deprecatedIds`), `:286-318` (`buildRedirectIndex`, scans every YAML's `mergedInto`/`aliases`), `:205-224` (alias validation) and `:241-267` (connection-target redirect resolution); schema at `data/issues/_schema.json` (`aliases`, `mergedInto` properties, no companion rationale field); connections schema at `data/issues/_schema.json:104-117` (no `id`, no redirect fields).
- **What**: The project has already built, tested, and shipped a full identity-redirect apparatus for one entity type — issues. `aliases`/`mergedInto` are live fields (14 of 353 issue files use `aliases`; `buildRedirectIndex` runs over all 353 on every validation pass), the validator resolves dangling connection targets through `aliasToCanonical`/`mergedToCanonical` (`:258-267`), and four surface modules (`router.ts`, `wiki.ts`, `palette.ts`, `dataLoad.ts`) independently honor the same redirect map end-to-end so an old citable address still resolves after a merge. Ruling 2 promises an analogous continuity guarantee for the 129 reconciled edge pairs — a losing claim should not simply vanish — but the connections schema (`_schema.json:104-117`) has no `id`, no `supersedes`/`redirectsTo` field, and no rationale field, and nothing in the brainstorm or the validator reuses the exact pattern already proven for issues. Even the existing precedent is only half an apparatus: `mergedInto` redirects an address but carries no companion field for who ordered the merge or why, so copying it verbatim for connections would satisfy machine-checkable resolution but still not satisfy Ruling 2's implied attribution.
- **Evidence**: `grep -l '^aliases:' data/issues/*.yaml` → 14 files (live usage); `grep -l '^mergedInto:' data/issues/*.yaml` → 0 (mechanism built and exercised by the validator, not yet triggered by real data); `grep -n 'mergedInto\|redirects' src/main/router.ts src/main/wiki.ts src/main/palette.ts src/main/dataLoad.ts` → all four modules consume the same redirect concept; `data/issues/_schema.json` properties list has `aliases` and `mergedInto` for issues but no matching fields under `connections` (`:104-117`).
- **Suggestion**: Give each `connections[]` entry the same shape already proven for issue identity — one stable `id`, one optional `supersedes`/`redirectsTo` pointing at the id of the claim it replaced, one `rulingRef` naming the deciding authority — and extend `buildRedirectIndex`'s pattern (not a new subsystem) to index reconciled-pair history the way it already indexes merged issue ids.
- **intersection_justification**: The ontology parent, reading `validate-issue-data.ts` and `_schema.json` in isolation, would call the alias/merge mechanism "done" — it is a working redirect index with real coverage — and would separately flag connections' missing `id` field as a generic schema gap, without noticing the first thing is a ready-made template for the second. The apparatus parent, reading only the brainstorm's Ruling 2, would ask for a preserved dispute and a named authority in the abstract, without ever opening `validate-issue-data.ts` to see that the project has already built, wired end-to-end, and shipped exactly that continuity guarantee once — for a different entity type, and stopping one field short of attribution even there. Only holding both readings together surfaces the actual finding: the smallest fix is not a new mechanism but reusing an existing, tested one that is sitting unused right next to the code that needs it, and even that reuse would leave the rationale half unmet.

### reciprocal-pair-shape-conflates-loop-with-contradiction

- **Severity**: P0
- **Where**: `data/issues/_schema.json:104-117` (`connections` item schema: `target`, `relationship` enum of `causes|exacerbates|mitigates|correlates|blocks`, `strength` — no field for pair role or disposition); `scripts/data/validate-issue-data.ts:241-267` (connection validation checks only that targets resolve; no reciprocal-pair inspection at all); brainstorm Key Decisions #2 (129 pair rulings, one winner written to YAML) and #8 (Jev does "the 129 pair rulings and the 30 two-cycle checks").
- **What**: Ruling 8 names two distinct judgment tasks over reciprocal edges — 129 pairs that are contradictions to be resolved to one winner, and 30 "two-cycle checks" that are presumably legitimate reinforcing loops (A and B each drive the other) to be kept as-is. A direct scan of the 353 YAML files' `connections[]` for reciprocal pairs (A→B and B→A both present) finds 109 symmetric `correlates`/`correlates` duplicates (not contradictions — correlates is symmetric by construction) and 151 pairs where the two directions carry different or repeated asymmetric relations. Splitting those 151 by relation combination: `causes`+`causes` (1) + `exacerbates`+`exacerbates` (20) + `causes`+`exacerbates` (9) = 30 — the "mutually reinforcing" combinations, exactly matching Ruling 8's "30 two-cycle checks" — while the remaining ~121 mixed combinations (`correlates`+`exacerbates`: 72, `causes`+`correlates`: 40, `correlates`+`mitigates`: 3, `blocks`+`correlates`: 2, and five singletons) are the candidates for the "129 pair rulings." The two categories that Jev is commissioned to tell apart are, in the data model, the identical shape: two `connections[]` entries with a `target` and a bare `relationship` string, no pair id, no `disposition` field. Once Jev finishes and Ruling 2's validator becomes a "129-pair exception list" (already noted as the only mechanism available), that list has no schema-level way to avoid also matching, or failing to protect, the 30 legitimate two-cycles it must leave untouched — because after judgment, a kept two-cycle and an unreconciled contradiction that slipped through both look like "two `connections[]` entries pointing at each other," full stop.
- **Evidence**: computed from `data/issues/*.yaml` connections (353 files, 1,852 edges): reciprocal directed pairs = 520 total; 109 are `correlates`/`correlates`; 151 are non-symmetric-duplicate; of those 151, relation-combination counts are `{('correlates','exacerbates'): 72, ('causes','correlates'): 40, ('exacerbates','exacerbates'): 20, ('causes','exacerbates'): 9, ('correlates','mitigates'): 3, ('blocks','correlates'): 2, ('causes','causes'): 1, ('blocks','mitigates'): 1, ('exacerbates','mitigates'): 1, ('mitigates','mitigates'): 1, ('causes','mitigates'): 1}` — the `causes`+`causes`/`exacerbates`+`exacerbates`/`causes`+`exacerbates` subset sums to exactly 30; the rest sums to ~121, within rounding of the ruled 129. `_schema.json:104-117` connections item schema has no field beyond `target`/`relationship`/`strength`.
- **Suggestion**: Add one `pairRole` (or `disposition`) enum to the connections item schema — `reconciled-winner` / `reconciled-superseded` / `verified-loop` — set by Jev's output for exactly these 151 (not 1,852) edges, so `data:validate` can assert "every reciprocal pair has a disposition" instead of matching pair ids by hand, and a verified loop is structurally inert against future contradiction-detection rules.
- **intersection_justification**: The ontology parent, working from the declared relation types alone, would flag that `causes`+`causes` or `exacerbates`+`exacerbates` reciprocal edges have no declared cycle-legality rule and stop there — a generic "is this a permitted cycle" schema question, answerable without knowing anything about the 129/30 split or which specific pairs are which. The apparatus parent, working from Ruling 8's text alone, would ask that Jev's disposition be recorded and attributed, without the corpus-level count showing that the recording gap is not hypothetical: the exact 151 reciprocal pairs Jev must classify already exist, already split almost precisely 30/121 along the lines Ruling 8 names, and already share one undifferentiated schema shape. The fused reading is what makes the failure concrete and countable rather than a generic "add a status field" suggestion: a specific, already-existing 151-edge set is about to be judged into two dispositions that the schema cannot then distinguish, which is exactly the P0 erasure scenario in this lens's own calibration, now pinned to real rows instead of an abstract 129.

## Verdict

Both findings survive the fused hard constraint because each depends on a fact only visible by reading the ontology/validator code and a fact only visible by reading the brainstorm's ruling text side by side — neither a pure schema audit nor a pure apparatus reading would produce either finding alone. The first (P1) shows the project already possesses, and does not reuse, a cheaper-than-expected fix for the ruling's own flagged erasure risk. The second (P0) sharpens that same erasure risk from a hypothetical into a specific, counted 151-edge set that the schema cannot tell apart into "kept loop" versus "resolved dispute" the moment Jev's judgments are written back.
