## Findings

### stale-evidence-base-head
- **Severity**: P0
- **Where**: the reviewed checkout `/Users/sma/projects/shadow-workipedia` (the evaluation doc's own header: "Repo HEAD 632e730"); compare `origin/main` after `git fetch origin main`.
- **What**: A qanat crew never cuts a new stretch without re-sounding the mother well first — the water table moves. This review re-sounded it: `git fetch origin main` shows the checkout the evaluation and brainstorm were built on (`632e730`, 2026-07-14) is **3 commits behind `origin/main`** (now `b0cb582`, 2026-09-01). One of the three missing commits is titled, verbatim, `chore(data): regenerate wiki data from real-names sources`. That is not an unrelated commit — it is a wiki-regeneration pass in exactly the domain ruling 3 ("one source of truth," migrating wiki frontmatter into YAML and deleting the scrapers) and ruling 5 (mechanics prose regenerated from what the engine consumes) propose to redo. Every count the plan reasons from — 353 issues, 156/353 urgency mismatches, 98/353 category mismatches, 129 contradictory pairs, "wiki last touched Dec 23" — was measured against a snapshot that a real, already-merged commit has since altered by an unmeasured amount. Ruling 9's "Week 0: router crash + YAML precedence" sequencing assumes the current checkout is the starting line; it is actually a fork of the starting line taken two and a half months ago.
- **Evidence**: `git fetch origin main` (run 2026-09-19) → `632e730..b0cb582 main -> origin/main`; `git log -1 --format='%ad %H %s' origin/main` → `2026-09-01 b0cb5822... chore(data): regenerate wiki data from real-names sources - mnht`; evaluation doc header: "Date: 2026-09-19 · Repo HEAD 632e730"; `git rev-list --left-right --count origin/main...HEAD` → `3  0` (3 commits present on origin/main and absent from the reviewed HEAD, 0 the reverse).
- **Suggestion**: Before executing any ruling, `git pull --ff-only` (or rebase) the checkout onto `origin/main` and re-run the extractor/comparison that produced the evaluation doc's counts. If the September commit already regenerated wiki content that changes the mismatch percentages, revise rulings 3/5's scope and the labour arithmetic in ruling 7 before Week 0 starts — don't discover the discrepancy mid-sprint when the data track's own commits start conflicting with unpulled upstream history.

### orphan-wiki-generation-clone
- **Severity**: P1
- **Where**: `/Users/sma/projects/shadow-work/scripts/data/generate-wiki-from-yaml.ts:15` (`const WIKI_DIR = join(process.cwd(), 'shadow-workipedia/wiki/issues');`, written to at line 264 after `mkdirSync` at lines 221-222); read side is `/Users/sma/projects/shadow-workipedia/scripts/parse-wiki.ts:152` (`const wikiRoot = join(process.cwd(), 'wiki');`), consumed by `extract-data.ts:1923` (`loadWikiContent()`).
- **What**: A qanat's write-crew and draw-crew must be cutting toward the same shaft, or the water never reaches the village cistern even though both crews report progress. Here they are provably not: `generate-wiki-from-yaml.ts` resolves its output relative to `process.cwd()` plus a hardcoded `shadow-workipedia/` segment — it assumes shadow-workipedia is nested *inside* shadow-work. It is not; they are sibling checkouts (`/Users/sma/projects/shadow-work` and `/Users/sma/projects/shadow-workipedia`, confirmed by `git remote -v` on each: `gensysven/shadow-work.git` and `gensysven/shadow-workipedia.git` respectively). The path only resolves at all because a *third*, independent clone of shadow-workipedia happens to sit nested at `/Users/sma/projects/shadow-work/shadow-workipedia` (its own `.git`, same origin, HEAD already at `b0cb582` — the current tip). That nested clone additionally carries **uncommitted local modifications** to `public/agent-data.pack`, `public/agent-vocab.v1.json`, `AGENTS.md`, `package.json` and two files under `docs/plans/` — generated-artifact classes the data track will also touch. Meanwhile `shadow-workipedia`'s own `package.json` (the repo this brainstorm's document lives in) defines no `data:generate-wiki`, `data:validate` or `data:migrate-wiki` script at all — those exist only in shadow-work's `package.json:184-190`. So there is no single command, run from any one working copy, that both regenerates wiki content and is guaranteed to land where `parse-wiki.ts` and `extract-data.ts` in *this* checkout will read it. Ruling 9 calls the data track's territory "`scripts/`, `data/issues/`" as if it were one addressable place; it is actually two repositories plus a third accidental clone, and the one clone that currently matches origin/main's tip is the one nobody's sequencing plan names.
- **Evidence**: `generate-wiki-from-yaml.ts:14-15` (`DATA_DIR = join(process.cwd(), 'data/issues')`, `WIKI_DIR = join(process.cwd(), 'shadow-workipedia/wiki/issues')`); `parse-wiki.ts:152,154` (`wikiRoot = join(process.cwd(), 'wiki')`); nested clone confirmed via `ls -la /Users/sma/projects/shadow-work/shadow-workipedia` (has its own `.git`) and `git remote -v` there → `origin https://github.com/gensysven/shadow-workipedia.git`; nested clone `git status --short` lists 10 modified/generated-artifact paths; `shadow-workipedia/package.json` scripts block (dev, build, build:full, preview, preview:full, extract-data, generate:mechanics, normalize:mechanics, fill:mechanics, audit:mechanics, backfill:issue-mechanics, typecheck, test:narration, prepare) contains no `data:*` verb; `shadow-work/package.json:184-190` defines `data:migrate-wiki`, `data:generate-wiki`, `data:validate`, `data:normalize-affected-systems`, `data:audit-affected-systems`, `data:apply-audit-affected-systems`, `data:dataset-index:refresh`.
- **Suggestion**: Fix `WIKI_DIR` in `generate-wiki-from-yaml.ts` to take an explicit, environment-configured path (or a documented sibling-checkout convention) instead of assuming nesting, and reconcile or retire the accidental nested clone before ruling 3's migration starts. Separately, name in ruling 9 which of the two `shadow-workipedia` working copies the data-track commits are meant to land in — "disjoint files" is not the same claim as "disjoint, mutually-unaware git histories."

## Verdict
Both findings are load-bearing, not decorative: the evaluation doc's every count and the brainstorm's every ruling were measured against a checkout that is provably stale against its own remote, and the one pipeline command CLAUDE.md documents for regenerating wiki content resolves, by an unexamined relative-path assumption, into a second clone this checkout never pulls from. Reconcile the git state and name a single canonical wiki-generation target before ruling 9's Week 0 begins — otherwise the data track's first real commits will land on top of, or silently diverge from, work that already happened two and a half months ago in a different shaft.
