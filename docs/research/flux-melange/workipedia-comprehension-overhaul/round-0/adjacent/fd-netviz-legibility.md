## Findings

### ego-focus-fails-at-hub-nodes
- **Severity:** P0
- **Where:** Key Decision #1 ("labels, seeded layout, legend, typed edges, ego-focus" as the legibility plan) and Key Decision #6 ("`correlates` stays on by default... density is therefore solved by encoding... not by subtraction").
- **What:** I computed per-issue degree directly from `data/issues/*.yaml` `connections` (353 files, 1,852 total edges, mean degree 10.5, median 8). The distribution has a long tail: `democratic-backsliding` (67 edges: 35 correlates / 25 exacerbates / 7 causes), `trust-collapse-across-all-institutions` (60 edges: 16 causes / 38 exacerbates / 6 correlates), `mental-health-apocalypse` (55 edges: 19 correlates / 30 exacerbates / 5 causes / 1 mitigates), `climate-refugee-floods` (53 edges: 22 correlates / 17 exacerbates / 13 causes / 1 mitigates). Ego-focus is the plan's named tool for taming density at a node of interest, but for the node a comprehension-focused newcomer would most plausibly land on — `trust-collapse-across-all-institutions`, a hub with almost no `correlates` at all — hiding or de-emphasizing `correlates` (ruling 6's stated compensating mechanism) removes only 6 of 60 edges. The node still radiates 54 causal/exacerbates edges even under the plan's own legibility tool with its weakest relation fully suppressed. This is the exact failure the lens's severity rubric describes: the compound density problem persists at the precise spot the overhaul exists to fix, because the density here is intrinsic to the node's true relational load, not an artifact of `correlates` inflation.
- **Evidence:** Computed via `data/issues/*.yaml` connections parse (this session): degree tally and relation-type breakdown per node, reproducible with any YAML-walking script over the 353 files; evaluation doc corroborates edge-type counts overall ("1,852 issue-issue edges carry causes (194), exacerbates (582), correlates (1,047), mitigates (22)").
- **Suggestion:** Cap ego-focus's rendered edge count independent of relation type (e.g., show top-N by strength/weight, or a "+43 more, filtered by type" affordance) rather than relying on relation-type dimming alone to reach a readable fan-out — the plan needs a degree-based fallback for the ~15-20 issues above degree ~30, not just a type-based one.

### seed-derived-from-live-content-breaks-under-concurrent-edits
- **Severity:** P1
- **Where:** Key Decision #1 ("seeded layout so positions are stable across loads"); Key Decision #9 (data and surface tracks run concurrently, "rejoining where typed edges need reconciled relations"); `src/graph.ts` lines 53-54, 61-68.
- **What:** The current implementation seeds every node position with `width/2 + (Math.random()-0.5)*100` / `height/2 + (Math.random()-0.5)*100` before running `forceSimulation` — confirmed unseeded, matching the evaluation doc's finding that layout differs on every load. There is no coordinate-snapshot file, cache key, or layout-versioning code anywhere in `src/`. "Seeded" most naturally gets implemented as a deterministic hash of node/edge content feeding a PRNG — but ruling 9 has the data track actively reconciling 129 edge pairs and retyping 353 issues (ruling 4) in parallel with the surface track building this exact layout. Any content-derived seed changes every time an edge is reconciled or an issue is retyped, which ruling 9 guarantees happens repeatedly during the months both tracks run. Users would lose spatial memory during precisely the period the overhaul is trying to build trust in the data.
- **Evidence:** `src/graph.ts:53-54` (`Math.random()` position init), `:61-68` (`forceSimulation`/`forceLink`/`forceManyBody`/`forceCenter`/`forceCollide` construction, no seed parameter anywhere); no `*.json` coordinate cache found under `public/` or `data/` in either repo.
- **Suggestion:** Pin the seed (or the resulting coordinates) to something decoupled from live edge/type content — e.g., seed off `id` alone (stable identity, not connections), or check in a coordinate snapshot regenerated only on an explicit "relayout" step, not on every `data:validate`/build run — so the data track's edits don't silently invalidate the surface track's stability guarantee.

### timeline-ships-against-mostly-undated-corpus
- **Severity:** P1
- **Where:** Key Decision #7 ("far-future issues are written so the corpus spans 2025–2525, and a timeline surface is built across it"); Open Questions ("Is the timeline a view or a filter?", "Who authors the far-future issues, and how many are needed before 2025–2525 is honest?").
- **What:** The evaluation doc's own numbers: `peakYears` covers 236/353 issues, of which 149 start between 2000 and 2024 and only 10 reach past 2100 — against a stated 2025-2525 premise spanning five centuries. Ruling 9's sequencing puts the timeline surface in the same "surface track" bucket as the rest of the legibility work, with no gate on ruling 7's authoring progress; ruling 7 itself has no numeric target (the Open Question literally asks "how many are needed"). If the timeline ships before enough far-future issues are authored, its default view over a 2025-2525 axis would show the ~3% of the corpus that currently reaches past 2100, which is worse than no timeline at all for comprehension — it looks like the catalog barely extends past the present.
- **Evidence:** Evaluation doc: "`peakYears` covers 236/353; 149 of those start between 2000 and 2024, and 8 start before 2000 (one in 1925), and only 10 reach past 2100 against a stated 2025-2525 premise."
- **Suggestion:** Gate the timeline's ship date on a stated minimum coverage threshold across the 2025-2525 range (not just "some issues authored"), and answer the lens-adjacent Open Question explicitly: if the timeline is also the density filter, its usefulness as a filter is capped by the same sparse-coverage problem until ruling 7 clears that threshold.

### canvas-only-legend-has-no-accessible-counterpart
- **Severity:** P2
- **Where:** "What We're Building" ("Alongside both: the router crash, the 18 MB payload, the 747-row table, mobile, and the keyboard and screen-reader paths"); Key Decisions #1-9 (accessibility not named in any numbered ruling after that one mention).
- **What:** The existing rendering pattern (`src/main/graphUtils.ts`, community-hull labels via `fillText`) is entirely canvas-drawn with no parallel DOM nodes. The plan's legibility fixes — labels, a legend, typed/directed edges — are specified in the same register ("a legend card with entity counts" is cited approvingly from the Ontology view, itself presumably canvas-rendered like the flagship graph). Nothing in the nine numbered Key Decisions assigns an owner, a design, or a checkpoint to the accessible/DOM-parallel path implied by "keyboard and screen-reader paths" in the opening paragraph — it appears once, in a list of leftover items, and never again. Given the sequencing ruling (9) only names the data/surface split and a router+YAML unblock step, accessibility has no place in the plan where it would be checked before ship.
- **Evidence:** Evaluation doc S13: "The canvas has no `role`, no `aria-label`, no keyboard path... Search input unlabeled... No `prefers-reduced-motion` rule anywhere in 3,813 lines of CSS"; brainstorm's single mention of "keyboard and screen-reader paths" with no corresponding Key Decision or sequencing step.
- **Suggestion:** Add a tenth ruling (or fold into ruling 9's sequencing) that specifies the accessible representation's form — most likely an off-canvas, ARIA-live node/edge list synchronized to the same data the canvas renders — and a point in the data/surface rejoin where it's verified, not left to be inferred from "alongside both."

### mobile-has-no-track-assignment
- **Severity:** P3
- **Where:** "What We're Building" ("Alongside both: the router crash, the 18 MB payload, the 747-row table, mobile, and the keyboard and screen-reader paths").
- **What:** S12's mobile findings (tab nav clipped, chips run off-screen, Reset unreachable, canvas cut off at 390px) are bucketed with the router crash and payload size as a leftover item, but a force-directed canvas holding 353+ nodes at mobile viewport width is a materially different rendering problem than the desktop legibility techniques Key Decision #1 commits to (different label sizing, touch hit-testing instead of hover, no room for a persistent legend). Ruling 1 explicitly commits to the graph as the front door; nothing says whether that commitment includes a mobile-specific layout/interaction mode or defers mobile legibility to a later phase.
- **Evidence:** Evaluation doc S12 (tab nav, chip overflow, Reset unreachable, canvas cut off at 390px; "CLAUDE.md documents 768/480 stacking that does not happen").
- **Suggestion:** State explicitly whether ruling 1's "graph stays home" applies at mobile width too, or whether mobile gets a distinct (e.g., list-first) home view during this overhaul — leaving it implicit risks the surface track treating "mobile" as a subset of the desktop legibility fixes when it needs its own design pass.

## Verdict
The plan's techniques work for a typical node (median degree 8) but not for the handful of hub nodes — up to degree 67, dominated by `causes`/`exacerbates` rather than the `correlates` ruling 6 targets — that a comprehension-focused visitor would most want to inspect, so "legible by encoding alone" fails exactly where the overhaul's stakes are highest. The remaining risk is less about wrong techniques and more about missing prerequisites the sequencing ruling doesn't provide: a content-decoupled coordinate snapshot for the seeded layout, a minimum-coverage gate before the timeline ships, and an assigned owner for the accessible and mobile paths that currently exist only as a trailing mention.
