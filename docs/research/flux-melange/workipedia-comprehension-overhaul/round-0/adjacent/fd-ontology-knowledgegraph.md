## Findings

### validator-has-no-axioms-to-generalize-from
- **Severity:** P0
- **Where:** Key Decision #2 ("a validator keeps the 130th from being committed"); `scripts/data/validate-issue-data.ts` (392 lines, in `/Users/sma/projects/shadow-work`); `data/issues/_schema.json` `connections.relationship` enum; `public/ontology.json`.
- **What:** The brainstorm states the 129 contradictory edge pairs are reconciled "in the source" and a validator in `data:validate` stops a 130th from landing. I verified the current `validate-issue-data.ts` (wired to `pnpm data:validate` alongside `normalize-affected-systems.ts --check`) does per-file Ajv schema validation plus staleness heuristics — `grep` for `relationship|contradict|reverse|inverse|correlates|causes|exacerbates|bidirectional` returns zero hits. There is no cross-file edge-pair check today, and — more importantly — there is nowhere in the repo (`_schema.json`, `public/ontology.json`, or the brainstorm itself) that declares which relations are inverses of which, which are symmetric, or what domain/range each relation type is restricted to. `public/ontology.json`'s only `range` fields (lines ~350-378) are numeric bounds for agent `ideology_axes`, unrelated to the five issue-relation types. Without that axiom table, a "validator" checking pair consistency has no general rule to evaluate against — it can only enumerate the known 129 IDs and flag exact matches, which is precisely the failure mode the lens's own severity rubric calls out: a hardcoded list that ships any newly-authored or newly-edited contradictory pair silently, because nothing structural said the 130th pair was even checkable.
- **Evidence:** `scripts/data/validate-issue-data.ts` functions are `collectStringValues`, `addStalenessHeuristicWarnings`, `loadSchema`, `validateFile`, `buildRedirectIndex`, `main` — all per-file or redirect-index concerns, none graph-level. `_schema.json`'s `connections.relationship` is `{"enum": ["causes","exacerbates","mitigates","correlates","blocks"]}` with no companion inverse/symmetry metadata. Evaluation doc: "129 of 260 reversed pairs carry contradictory labels... All edges are `bidirectional: false`."
- **Suggestion:** Before wiring the validator, add a small relation-axioms table (e.g. `data/issues/_relations.json`: `causes.inverse = null` (asymmetric, no reverse expected), `correlates.symmetric = true`, `exacerbates.inverse = null`, `mitigates.inverse = null`, `blocks.inverse = null`) and have the validator derive its check from that table — "for every unordered pair with edges in both directions, do the relation types satisfy the declared symmetry/inverse rule" — rather than hand-listing the 129 known offenders. That turns the one-time cleanup into a durable, re-derivable invariant, which is the property Key Decision #2 claims but doesn't yet have a mechanism for.

### taxonomy-mismatch-not-hypothetical
- **Severity:** P1
- **Where:** Key Decision #4 ("Every issue carries one of `ontology.json`'s 18 `issue_types`"); Open Questions #1 ("Does the engine's taxonomy fit the content?"); `public/ontology.json` `issue_types` array; `data/issues/*.yaml`.
- **What:** `public/ontology.json`'s 18 `issue_types` are `sovereign_debt_crisis, currency_crisis, trade_war, recession, hyperinflation, mass_unemployment, class_conflict, migration_crisis, demographic_cliff, legitimacy_crisis, corruption_scandal, electoral_crisis, coup_risk, oil_shock, resource_depletion, climate_disaster, automation_displacement, technology_gap` — a macro-economic/geopolitical crisis archetype set paired with 12 `pressure_types` and 8 `institution_types`, generated by "the Rust emergence stack" for its own state-machine simulation. The 353 authored issues in `data/issues/*.yaml` are far narrower and more heterogeneous: `academic-replication-crisis-and-fraud`, `accessibility-compliance-failure`, `abortion-access-crisis`, and (from the evaluation doc) things like the AMOC Collapse, Permafrost Methane Release, and a "TikTok challenge kills 12 in 48 hours" scenario headline. None of these map to exactly one of the 18 types by any criterion the brainstorm states — `academic-replication-crisis-and-fraud` isn't a `legitimacy_crisis`, a `corruption_scandal`, or a `technology_gap` cleanly; `accessibility-compliance-failure` fits none of the 18 at all. The brainstorm's own Open Questions section treats "does the taxonomy fit" as a live unknown requiring a threshold and a ruler, but Key Decision #4 is already stated as settled ("Every issue carries one of the 18") — the decision assumes the answer to the question it hasn't yet asked.
- **Evidence:** `public/ontology.json` lines ~19-37 (`issue_types` array); `data/issues/` file listing (353 files, sampled `abortion-access-crisis.yaml`, `accessibility-compliance-failure.yaml`, `academic-replication-crisis-and-fraud.yaml`); evaluation doc's "Additional findings" section: "Two ontologies coexist unconnected: `public/ontology.json`... 18 issue *types*... and the 353-instance content catalog the engine does not read."
- **Suggestion:** Run the typing pass (ruling 8's Jev judgment work) with a mandatory low-confidence/no-fit flag before treating Key Decision #4 as closed, and pre-register the threshold from Open Questions #1 (e.g. "if >15% of issues score low-confidence across all 18 types, that's a taxonomy-gap finding, not a forced assignment") rather than discovering it after 353 issues are already committed to types.

### cascade-edges-no-shared-vocabulary
- **Severity:** P1
- **Where:** Key Decision #4 ("the 24 engine `cascade_edges` are reconciled against the authored 1,852"); Open Questions #2 ("Where the 24 engine `cascade_edges` and the 1,852 authored edges conflict, which wins?"); `public/ontology.json` `cascade_edges` array.
- **What:** The 24 `cascade_edges` in `public/ontology.json` connect the 12 `pressure_types` to each other (e.g. `economic_strain → social_unrest`, weight 0.2) — they are a small, hand-built state-transition graph over abstract simulation pressures, not over issues. The 1,852 authored edges connect 353 concrete issue instances. "Reconciling" or finding "conflicts" between these two graphs presupposes a projection — which issues instantiate which pressure_type(s) — that no ruling, open question, or schema field defines. Open Question #2 asks "which wins when they conflict," but a conflict isn't even expressible yet: there's no edge in either direction between, say, `democratic-backsliding` (an issue) and `legitimacy_crisis` (a pressure_type) to compare against `economic_strain → social_unrest`. This is a harder, prior problem to the one the brainstorm poses.
- **Evidence:** `public/ontology.json` `cascade_edges` (24 entries, all `{source, target, weight}` pairs drawn only from the 12-item `pressure_types` list); `_schema.json` has no `pressure_type` or `issue_type` field on the issue object at all today (only `categories`, `connections.relationship`, `affectedSystems`).
- **Suggestion:** Treat "define the issue → pressure_type mapping" as its own ruling (or fold it into ruling 4 explicitly) before Open Question #2 can be answered — the tie-break rule needs a shared vocabulary to operate on first.

### loop-count-computed-pre-reconciliation
- **Severity:** P2
- **Where:** "Why This Approach" paragraph 4 ("What a build-time graph does buy is derivation the site cannot hand-author — including the 94 reinforcing feedback loops latent in the `causes` + `exacerbates` subgraph").
- **What:** The evaluation doc's 94-loop count ("the `causes` + `exacerbates` subgraph contains 94 distinct reinforcing feedback loops... none surfaced") is cited by the brainstorm as a concrete justification for building the ontology/graph layer. But that count was computed over the current, pre-reconciliation edge set, which still contains the 129 contradictory pairs this same brainstorm commits to fixing (72 of them are exactly `correlates`/`exacerbates` conflicts — i.e., edges that may flip category or disappear once ruled). No ruling schedules a recount after reconciliation, so the "94" that sells the feature to stakeholders may not match the number the shipped feature actually surfaces, which is a minor trust cost after the overhaul's entire premise is fixing numbers that don't match reality.
- **Evidence:** Evaluation doc "Additional findings": "94 distinct reinforcing feedback loops (30 of length 2, 18 of 3, out to length 6)"; same doc's Review corrections: "129 of 260 reversed pairs carry contradictory labels — correlates/exacerbates 72, causes/correlates 40..."
- **Suggestion:** Add "recompute and re-report the loop count" as an explicit acceptance step after ruling 2's reconciliation lands, before it's used in any user-facing copy or success metric.

### no-schema-versioning-for-taxonomy-growth
- **Severity:** P2
- **Where:** Key Decision #4; `public/ontology.json` top-level `schema_version` field.
- **What:** `public/ontology.json`'s `schema_version` is `"2.0.0-p12i8t18f31"` — a single opaque string with no changelog or migration mechanism visible anywhere in the repo. If the typing pass (ruling 8) confirms the taxonomy-gap risk in `taxonomy-mismatch-not-hypothetical` above and the engine grows past 18 `issue_types`, nothing in the ruled design says whether the 353 already-typed issues get re-evaluated against the new taxonomy or silently keep their old (possibly now-wrong) type. Ruling 8 governs judgment quality (dual-rater on low-lift rows) but not schema migrations.
- **Evidence:** `public/ontology.json` line 2: `"schema_version": "2.0.0-p12i8t18f31"`, no companion migration script or version-diff tooling found under `scripts/`.
- **Suggestion:** Decide now (even if the answer is "re-run the full typing pass on any taxonomy version bump") rather than after the first version bump forces the question under time pressure.

## Verdict
Rulings 2 and 4 both assume an axiom layer that doesn't exist in the repo yet: the schema has five relation-type strings with no declared inverse/symmetry/domain-range, and the engine's 18 issue_types were built for a different simulation object (pressure_types) than the 353 narrative issues now expected to absorb them. The 129-pair validator and the cascade-edge reconciliation are the same missing-foundation problem wearing two ontology hats — build the relation axioms and the issue↔pressure_type mapping first, or both will degrade into ad hoc, silently-incomplete patches exactly where the brainstorm needs them to be durable.
