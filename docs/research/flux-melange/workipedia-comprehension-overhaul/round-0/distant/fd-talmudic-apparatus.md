## Findings

### edge-identity-missing-for-reconciliation

- **Severity:** P1 — attacks an unstated assumption beneath Rulings 2 and 4, not the rulings themselves.
- **Where:** `src/types.ts:97-106` (`GraphEdge`: `source`, `target`, `type`, `strength`, no `id`); `/Users/sma/projects/shadow-work/data/issues/_schema.json:104-117` (`connections` items require only `target`; `relationship` and `strength` are optional with defaults; no id field).
- **What:** A relationship between two issues has no stable identity independent of its position in an array and its `(source, target)` pair. Ruling 2 promises the 129 contradictory pairs are "reconciled in YAML" and Ruling 4 promises the 24 engine `cascade_edges` are "reconciled against the authored 1,852" — both operate on "the edge" as a citable unit that a decision can attach to, but nothing in the data model can name a specific edge to say "this one was reconciled, in favor of X, superseding Y." `issueIdRedirects`/`canonicalIssueAliases` exist for issue identity (`src/types.ts:168-169`) with no analogue one level down for relationships.
- **Evidence:** Confirmed by reading both files directly. `_schema.json`'s `connections.items.required` is `["target"]` only — no id, no source-of-claim, no dispute-state enum value (`relationship` enum is `causes|exacerbates|mitigates|correlates|blocks`, nothing marking "disputed" or "superseded"). Quantified against the evidence base: 129 of 260 reversed pairs carry contradictory labels, all destined for the same identity-less reconciliation.
- **Suggestion:** Add a deterministic edge id (e.g. `${min(source,target)}::${relationship}::${max(source,target)}`, computed at build/validate time — no need to hand-author 1,852 ids) so the validator, the reconciliation record, and any future citation can address "this edge" instead of "this array position." Smallest viable version: a pure function in `validate-issue-data.ts`, not a schema migration.

### contradiction-validator-does-not-exist

- **Severity:** P1 — attacks Ruling 2 directly: the safety mechanism it names is not yet built and the schema has nowhere to put what it would need to record.
- **Where:** `/Users/sma/projects/shadow-work/scripts/data/validate-issue-data.ts` (392 lines, read in full) and `_schema.json:104-117`.
- **What:** Ruling 2 states "a validator in `data:validate` so they cannot regress." Grepping the actual validator for `reversed`, `bidirectional`, and `contradict` returns nothing — the file validates Ajv schema conformance, builds a `RedirectIndex` for issue-id merges/aliases, and runs staleness heuristics (time-sensitive phrasing, recent-year mentions). It contains no pairwise check that issue A's edge to B and issue B's edge to A agree, and the schema it validates against has no field to hold a "loses to" pointer, a rationale, or a deciding authority for a resolved dispute. The validator "so they cannot regress" therefore has to be built from nothing, against a schema with no representation for the thing it would be protecting.
- **Evidence:** Direct read of `validate-issue-data.ts` lines 1-392 and `_schema.json` connections block. Cross-checked against the evaluation doc's count: "129 of 260 reversed pairs carry contradictory labels... All edges are `bidirectional: false`" — confirming the reversed-pair relationship is exactly the shape this validator does not check.
- **Suggestion:** Smallest viable fix, one diff hunk each: (1) add an optional `supersededClaim: {relationship, rationale, decidedBy}` object to the `connections` item schema; (2) add one pass to `validate-issue-data.ts` that, for every `(A→B, B→A)` pair, asserts the relationships agree or one carries `supersededClaim` naming what it overrides. This is the field-plus-check the ruling's language already presupposes exists.

### reuse-redirect-index-for-edges

- **Severity:** P2 — a design-quality recommendation, not a corruption risk; folds into the same gap as the previous finding but is a distinct claim (a working precedent already exists in this codebase).
- **Where:** `/Users/sma/projects/shadow-work/scripts/data/validate-issue-data.ts:28-31, 286-318` (`RedirectIndex`: `aliasToCanonical`, `mergedToCanonical`, `deprecatedIds`).
- **What:** When two issue ids get merged, this project does not delete the losing id — it demotes it to `deprecatedIds`, records `mergedToCanonical`, and the validator uses that index to keep old references resolvable (lines 214-265). That is precisely the Talmudic move this lens looks for: preserve the superseded claim, attribute the resolution, keep it addressable. Ruling 2 needs the same shape one level down, for relationship claims instead of issue ids, but the brainstorm treats edge reconciliation as new work rather than "apply the merge/deprecate pattern we already trust."
- **Evidence:** Direct read of `buildRedirectIndex` (lines 286-318) and its three call sites (214, 258-265) — a working, tested mechanism already in the repo, not a hypothetical.
- **Suggestion:** Model the edge-reconciliation record on `RedirectIndex`: a `deprecatedEdges` set plus a `supersededBy` map, populated the same way `deprecatedIds`/`mergedToCanonical` are today. Ruling 2's implementers should be pointed at this file before designing a new mechanism.

### issue-type-field-and-cross-schema-drift

- **Severity:** P2 — matches the taxonomy-collapse risk this lens's own calibration names, with fresh grounding: the field doesn't exist yet, and nothing keeps it in sync with its source of truth.
- **Where:** `/Users/sma/projects/shadow-work/data/issues/_schema.json` (no `issue_type`/`issueType` property anywhere — confirmed by grep across the full file); `public/ontology.json` (`schema_version: 2.0.0-p12i8t18f31`, 18 `issue_types`, generated by the Rust emergence stack, a separate file with no cross-reference into `data:validate`).
- **What:** Ruling 4 says "every issue carries one of `ontology.json`'s 18 `issue_types`." The issue schema has no field for this today — it is entirely new schema surface, not an extension of an existing enum — and once added it would have no mechanism keeping its enum in sync with `ontology.json`'s list, which is generated independently by a different toolchain. Review Approach §3 (avot/toladot) asks whether typing "records a derivation... or only stamps a label" — right now there isn't even a label slot, and there's no path from "stamp a label" to "record why," so a flat, uninformative distribution across 353 issues would be structurally indistinguishable from correct typing (the lens's own P2 scenario), and a future 19th engine type would silently outrun an already-written enum with no build-time signal.
- **Evidence:** Grep for `issue_type`/`issueType` (case-insensitive) across `_schema.json` and `validate-issue-data.ts` returns zero matches. `ontology.json`'s `issue_types` array confirmed as 18 entries (`sovereign_debt_crisis` … `technology_gap`) living under its own `schema_version`, unrelated to the issue-data schema's `$id: "shadow-work-issue"`.
- **Suggestion:** Generate the `issue_type` enum in `_schema.json` from `ontology.json.issue_types` at validate time (a few lines in `validate-issue-data.ts`, not a hand-copied list, so the two never drift), and add an optional free-text `issueTypeRationale` field alongside it — the smallest version of a recorded derivation, not a new taxonomy layer.

### peak-years-still-freetext

- **Severity:** P2 — attacks an unstated assumption under Ruling 7 (that authoring more dates is purely a content task, not also a schema task); degrades quality rather than corrupting anything outright.
- **Where:** `/Users/sma/projects/shadow-work/data/issues/_schema.json:162-165` (`peakYears: { "type": "string", "description": "Historical or projected peak years" }`).
- **What:** Ruling 7 commits to giving 117 undated issues dates and authoring a corpus that spans 2025–2525. The only date-bearing field in the schema is `peakYears`, and it is an unconstrained free-text string — no format, no min/max, no numeric range. This is the same field shape the evaluation doc's own root-cause section cites as already producing wrong data downstream (urgency "invented by substring-matching free-text peak-year ranges," 44% disagreement with source) — cited here only as evidence for the structural claim, not restated as a finding of its own. Authoring 117 more values into that same unstructured field, then building a timeline surface that has to parse strings like "2025-2525" or prose ranges, repeats the shape that produced the original defect, and Ruling 7 doesn't propose changing the field before writing into it again. The evaluation's own count — "149 of 236 dated issues start between 2000 and 2024... only 10 reach past 2100 against a stated 2025-2525 premise" — is exactly the kind of drift a free-text field cannot be validated against.
- **Evidence:** Direct read of the schema property. Quantified against the evaluation doc: 236/353 issues currently have `peakYears`, 149 of those pre-2024, only 10 past 2100.
- **Suggestion:** Before the authoring pass, add a structured `peakYearRange: {start: integer, end: integer}` alongside (not replacing) the free-text `peakYears` prose. Gives the timeline a machine-sortable field and lets `data:validate` assert every far-future issue actually has a year past 2100, instead of authoring 117 more values into a field nothing can check.

## Verdict

Three of the nine rulings (2, 4, 7) commit to writing into a data model that does not yet have the field the ruling's own language presupposes — no edge identity for "reconciled," no `issue_type` slot for "unify with the engine," no structured year for "authored forward" — and the validator Ruling 2 names as the safety net has no logic for the exact defect it is meant to catch. None of this is a reason to reverse the graph-stays-home or correlates-on-by-default rulings, which are presentation choices this lens has no standing to contest; the gap is one layer down, in the ontology those surfaces will render. The fix in every case is the smallest kind this tradition prescribes — reuse the `RedirectIndex` shape the project already trusts, generate one enum from the other instead of hand-copying it, add one structured field beside the free-text one — not a redesign.
